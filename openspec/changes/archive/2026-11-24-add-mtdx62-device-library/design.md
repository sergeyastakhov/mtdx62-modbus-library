# Design

## Context

Требования — в `specs/mtdx62-registers/spec.md`, мотивация — в `proposal.md`. Исходные данные о
протоколе — `references/mtdx62/DEVICE-FACTS.md` в корне рабочего пространства.

Ограничения, которые задают устройство библиотеки:

- `modbus-connection` уже умеет всё, что нужно на уровне обмена: соединение, юниты, блочные
  чтения, повторы, бэкенды `tmodbus` и `pymodbus`. Библиотеке остаётся только карта регистров.
- Входные и holding-регистры — разные адресные пространства, планировщик не смешивает их в
  одном запросе.
- Модель обязана работать без Home Assistant, иначе тесты потребуют установленного Home Assistant
  и потеряют смысл.

## Goals / Non-Goals

**Goals**

- Один файл с картой регистров, который читается как даташит.
- Один запрос на опрос измерений.
- Тестируемость без железа: mock-бэкенд `modbus-connection`.

**Non-Goals**

- Запись параметров устройства.
- Активный отчёт устройства и подписка на события.
- Транспорт, повторы, таймауты — зона `modbus-connection`.
- Интерпретация порога освещённости как логики автоматизации: библиотека отдаёт числа.

## Decisions

### Решение 1: две подсистемы вместо одной плоской модели

`readings` описывает входные регистры, `settings` — holding-регистры. У каждой подсистемы свой
метод обновления.

**Почему.** Входные регистры меняются постоянно и читаются каждые 5 секунд, параметры меняются
редко и нужны только при разборе проблем. Разделение даёт правильную стоимость опроса: чтение
измерений — один запрос, параметры не читаются вовсе, пока их не попросят. Плоская модель
заставила бы либо читать всё вместе (два запроса на каждый опрос), либо прятать фильтрацию
внутри библиотеки.

**Альтернативы.** Один компонент на все регистры — лишние запросы при опросе. Отдельные
компоненты на каждое измерение — восемь запросов вместо одного.

### Решение 2: декларативные поля `modbus_connection.model`

Поля описываются готовыми хелперами: `boolean` для присутствия, `integer` для освещённости,
`gauge(0.01)` для расстояния, `raw_register` для кода состояния, `uint32` для сырых версий.
Пространство задаётся `register_space = "input"` у компонента измерений.

**Почему.** Планировщик сам складывает соседние адреса в один блок, а `boolean` и `uint32`
уже правильно разбирают крайние случаи (значение вне 0/1, порядок слов). Свой разбор пришлось бы
писать и тестировать отдельно, и он разошёлся бы с поведением остальных Modbus-интеграций.

**Альтернативы.** Ручной разбор байтов — дублирует библиотеку и теряет блочные чтения.

### Решение 3: версии и состояние — производные свойства, а не поля

`app_version`, `radar_version` и `status` — свойства поверх сырых полей. Сырые значения остаются
доступными.

**Почему.** Версия склеивается из двух регистров нестандартным образом (байты `0x00010203` = 1.2.3),
а код состояния может прийти неизвестным. Если бы это были поля, пришлось бы выбирать между
потерей исходного значения и разбором внутри декодера. Свойства дают и то и другое, а вызывающая
сторона сама решает, как показать «код неизвестен».

**Альтернативы.** Разбор в `convert` поля — неизвестный код превратился бы в `None` без остатка,
и диагностика потеряла бы исходное число.

### Решение 4: `distance` в метрах, шаг сантиметр

Поле объявляется как `gauge(0x0002, 0.01, unit="m")`, то есть значение в метрах с точностью до
сантиметра.

**Почему.** Регистр хранит сантиметры, но метры — единица, в которой расстояние осмысленно в
интерфейсе и в документации. Преобразование в сантиметры для показа делает интеграция, где
требуется целое число; здесь важно не терять точность.

### Решение 5: никаких собственных исключений

Библиотека не вводит свою иерархию ошибок: таймаут, ошибка протокола и отказ устройства приходят
из `modbus-connection`.

**Почему.** Своя обёртка заставила бы интеграцию разбирать два набора исключений, а различие
«таймаут» и «ошибка протокола» уже есть на уровне соединения. Единственное, что добавляет
библиотека, — ничего не глотает.

## Data Model

Постоянного хранилища нет: значения живут в атрибутах подсистем, пока объект устройства жив.

Карта регистров (полностью — в `references/mtdx62/DEVICE-FACTS.md`):

| Подсистема | Атрибут | Адрес | Поле модели |
|---|---|---|---|
| `readings` | `presence` | input `0x0000` | `boolean` |
| `readings` | `illuminance` | input `0x0001` | `integer`, ед. лк |
| `readings` | `distance` | input `0x0002` | `gauge`, шаг 0.01, ед. м |
| `readings` | `status_code` | input `0x0003` | `raw_register` |
| `readings` | `app_version_raw` | input `0x0004…0x0005` | `uint32` |
| `readings` | `radar_version_raw` | input `0x0006…0x0007` | `uint32` |
| `settings` | `detection_distance` | holding `0x0000` | `gauge`, шаг 0.01, ед. м |
| `settings` | `shielding_distance` | holding `0x0001` | `gauge`, шаг 0.01, ед. м |
| `settings` | `entry_delay` | holding `0x0002` | `gauge`, шаг 0.01, ед. с |
| `settings` | `departure_delay` | holding `0x0003` | `integer`, ед. с |
| `settings` | `trigger_sensitivity` | holding `0x0004` | `integer` |
| `settings` | `maintain_sensitivity` | holding `0x0005` | `integer` |
| `settings` | `entry_indent` | holding `0x0006` | `gauge`, шаг 0.01, ед. м |
| `settings` | `unit_id` | holding `0x0007` | `integer` |
| `settings` | `baudrate` | holding `0x0008` | `integer`, ед. бод |
| `settings` | `parity` | holding `0x0009` | `integer` |
| `settings` | `active_report` | holding `0x000A` | `integer` |
| `settings` | `light_threshold` | holding `0x000B` | `gauge`, шаг 0.01, ед. лк |
| `settings` | `report_interval` | holding `0x000C` | `integer`, ед. с |

Принадлежность `0x000B` и `0x000C` в документации противоречива — это открытый вопрос, который
проверяется на живом устройстве. На поведение библиотеки он не влияет: оба поля только читаются
для диагностики.

## Rule Boundary

Изменение не вводит бизнес-правил, проверок и новых путей исполнения: библиотека только читает
регистры и декодирует значения. Валидация адресов и параметров связи остаётся в интеграции, где
есть пользовательский ввод.

## Interface & Implementation Mapping

Не применимо: у библиотеки нет пользовательского интерфейса, её интерфейс — публичный API пакета,
описанный в спецификации.

## Risks / Trade-offs

- **Зависимость от `modbus-connection`** → библиотека следует за её версиями; ломающая правка
  контракта требует мажорной версии и обновления интеграции. Снимается тем, что версия
  фиксируется точно в `pyproject.toml`.
- **Неизвестный код состояния превращается в `None`** → интеграция обязана показать «код
  неизвестен», а не пустоту. Снимается тем, что `status_code` остаётся доступным.
- **Параметры читаются по требованию** → первый вызов диагностики будет медленнее (лишний
  запрос). Приемлемо: диагностика вызывается вручную.
- **Порог освещённости не используется** → поле читается, но не влияет на присутствие: логика
  порога живёт в устройстве. Снимается тем, что библиотека не претендует на эту логику.

## Migration Plan

Пакет новый, миграций нет. Публикация: `0.1.0` на PyPI, затем интеграция фиксирует
`mtdx62==0.1.0` в манифесте. Откат — снятие версии с PyPI и откат зависимости в интеграции.

## Open Questions

1. **Адреса `0x000B` и `0x000C`.** Примеры кадров в сканах противоречат друг другу: и порог
   освещённости, и интервал отчёта показаны по адресу `0x000B`. Проверка на живом устройстве:
   изменить порог пультом и посмотреть, какой регистр сдвинулся. До проверки поля остаются как
   в таблице, но в интеграцию не выводятся.
2. **Код MAC в `0x000D`.** В одном примере чтение MAC идёт по адресу `0x000C`. В эту версию не
   входит; понадобится, если интеграция перейдёт на идентификатор по MAC.
